Open-source local control center

ProductLoop Workbench

Give one operator a durable view of governed runs, exact approvals, evidence, memory links, policies, and proof exports without requiring a hosted account.

0.1.0 source candidate The implementation exists in the ProductLoop monorepo and passes its local build and test suite. It is not yet a public npm release. Do not use an npm install claim until the reviewed tarball, provenance, Git tag, GitHub release, and registry record match.

Start from the reviewed source

After the Workbench changes reach the public ProductLoop branch, build the exact source candidate locally:

git clone https://github.com/AjnasNB/productloop-os.git
cd productloop-os
npm ci
npm run build --workspace=productloop-workbench
node productloop-workbench/bin/productloop-workbench.js init
node productloop-workbench/bin/productloop-workbench.js demo
node productloop-workbench/bin/productloop-workbench.js serve

The server binds to 127.0.0.1:43120. The no-key demo uses deterministic local ProductLoop, Maqam, policy, approval, provenance, browser replay, and evaluation fixtures. It does not make a live browser, crawler, provider, model, or publish request.

Five operator surfaces

ApprovalsExact tool, effect, canonical input, digest, reviewer, and consumption stateProof that an external effect executed
EvidenceBounded records from ProductLoop, Maqam, Cockroach Browser, Cockroach Crawler, or custom adaptersTruth or source authorization

Exact approval lifecycle

  1. The host creates a durable run and records its purpose.
  2. Policy identifies a consequential operation.
  3. Workbench stores the exact tool, effect, risk, canonical input, and digest.
  4. A reviewer approves or rejects that specific proposal.
  5. Resume atomically changes one approved record to consumed.
  6. A trusted host independently verifies the binding and dispatches the real operation through Maqam.
  7. The host attaches the Maqam, browser, crawler, or provider receipt as evidence.
Approval is not dispatchA Workbench button updates a local review record. It never calls an external tool by itself. Consequential effects must still pass through the real enforcement boundary.

Durable local store

Workbench uses a SQLite database under .productloop-workbench by default. The database enables WAL journaling, full synchronous commits, foreign keys, bounded fields, transactional mutations, and a per-run hash-linked event ledger so each exported run contains its own verifiable chain. An approved decision can be consumed once by one local transaction.

This is single-operator local durability. It is not a distributed scheduler, shared database, cross-device synchronization system, backup service, or multi-tenant audit store.

Export the proof

node productloop-workbench/bin/productloop-workbench.js status --json
node productloop-workbench/bin/productloop-workbench.js export RUN_ID

A proof bundle contains the run, approval history, evidence, memory links, selected events, current integrity report, and a canonical bundle digest. Receipts make later modification detectable; they do not prove that a recorded external claim is true.

Security boundary

  • The dashboard is loopback-only, validates its exact active loopback Host, and uses a per-process API token.
  • Cross-origin or non-JSON mutations are denied, request bodies are capped at 64 KiB, and restrictive browser security headers are emitted.
  • The database may contain sensitive purpose text, inputs, evidence excerpts, and project metadata. Protect it accordingly.
  • Do not place API keys, tokens, cookies, private keys, or browser profile values in Workbench records.
  • Qarinah capture stays explicit per workspace and metadata-only by default.
  • Cockroach Browser and Crawler keep their own origin, profile, network, access, and content boundaries.
  • Maqam governs only operations routed through its configured gateway or adapter.
